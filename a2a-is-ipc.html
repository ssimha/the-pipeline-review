A2A Is IPC Wearing a Better Suit

Google's Agent2Agent protocol is being talked about like a new law of physics. It isn't. It's the fifth generation of a problem distributed systems engineers have been solving since the 1980s — and the genealogy tells you exactly what to trust, and what to double-check, before you wire two agents together.

Sirish Simha · The Pipeline Review

Every few years, distributed computing reinvents inter-process communication and gives it a new name so it feels like the industry has never solved this before. Sockets became RPC. RPC became SOAP. SOAP became REST and gRPC. Now REST and gRPC are becoming A2A — the Agent2Agent protocol, originally shipped by Google in April 2025 and handed to the Linux Foundation two months later, in June 2025, to run under neutral governance.

None of that is a criticism of A2A. It's a genuinely well-specified protocol solving a genuinely real problem: how does an autonomous agent built on LangGraph talk to one built on CrewAI, hosted by a company it has never integrated with, without a bespoke adapter for every pair? The point is different — if you understand A2A as IPC with a lineage, you stop being surprised by what it does, and you start asking the questions that lineage teaches you to ask: who's trusted, who's versioned, what happens when the other side is slow.

01 — LineageFour generations, one problem

Strip away the branding and every generation below is solving the same three things: how does one process find another, how do they agree on a message shape, and how do they survive the other side being unreachable.

Fig. 1 — IPC lineage stack
Each layer adds discovery and trust to the layer below it. A2A's actual novelty isn't the transport — it's what gets exchanged: capability descriptions and task state, not just data.

The honest way to read this stack: A2A didn't invent remote invocation. It inherited JSON-RPC's wire format, borrowed SSE from web streaming, and added one genuinely new layer on top — a discovery document (the Agent Card) that plays the same role a WSDL file played for SOAP or an IDL played for CORBA, except it describes what an agent can do rather than what functions it exposes.

02 — AnatomyWhat A2A actually specifies

Underneath the "agent" language, A2A is a small, disciplined spec. Four primitives do almost all the work:

PrimitiveRole
Agent CardA signed JSON document at a well-known URL announcing an agent's skills, auth requirements, and supported modalities — discovery, not execution.
TaskThe unit of work. Has an explicit lifecycle — submitted, working, input-required, completed, failed — so a caller always knows where a long-running job stands.
MessageA turn in the conversation between client and remote agent, carrying text, files, or structured data.
ArtifactThe output a task produces — a document, a dataset, a rendered result — returned as a first-class typed object, not buried in a text blob.

A2A reached its v1.0 milestone in early 2026, and the changes there are exactly what an IPC veteran would expect a maturing protocol to add: signed Agent Cards (so a receiving agent can verify a card actually came from the domain it claims to), multi-tenancy (one endpoint, many agents — useful for SaaS), dual bindings over both JSON-RPC and gRPC, and formal version negotiation between v0.3 and v1.0 clients. That is the same maturity curve SOAP, then REST, then gRPC each went through: ship loose, then bolt on identity and versioning once production traffic exposes the gaps.

Fig. 2 — client / remote agent exchange
Discovery (Agent Card) is separate from execution (Task). That split is the same reason WSDL sat apart from the SOAP call itself — it lets two parties agree on capability before they commit to a conversation.
The interesting engineering question was never "can two agents exchange JSON." It was always "who do you trust to have sent it, and what do you do when they don't answer in time." A2A's whole v1.0 changelog is that question, restated.

03 — EcosystemWhy Google gave it away

Google published A2A in April 2025 with roughly fifty launch partners, then donated the project to the Linux Foundation two months later — the same move it made with Kubernetes. A protocol that only Google controls is a protocol enterprises hedge against; a protocol governed by a neutral foundation, with a Technical Steering Committee seated by AWS, Cisco, Google, IBM Research, Microsoft, Salesforce, SAP and ServiceNow, is one they can build a five-year architecture on without worrying about a single vendor's roadmap.

It worked. By its one-year mark in April 2026, more than 150 organizations were supporting the standard, the reference implementation had passed 22,000 GitHub stars, and SDKs existed in five production languages beyond the original Python release. IBM's competing ACP effort folded into A2A in August 2025 rather than fight it. That's not a technical verdict — it's a governance verdict, and it's the more important one for anyone deciding whether to build on this.

The other piece worth being precise about: A2A is not competing with MCP, and framing them as rivals misunderstands both. MCP standardizes how a single agent talks to its own tools and data — the vertical connection. A2A standardizes how independent agents, built by different teams on different frameworks, talk to each other — the horizontal connection. You will very plausibly run both in the same system: MCP inside an agent, A2A between agents.

04 — So whatThe lineage is the point

If you've built anything on Sun RPC, SOAP, or gRPC, none of A2A's hard problems are new to you. Idempotency on retried tasks, backpressure when a remote agent is overloaded, versioning when a card changes shape, trust when a card claims a domain it doesn't own — these are IPC problems with forty years of prior art, now wearing agent-shaped clothes. The signed Agent Card in v1.0 exists because someone, somewhere, stood up a fake card and redirected traffic — the exact failure mode PKI solved for TLS certificates, rediscovered in a new context.

Treat A2A the way you'd treat any RPC generation you've adopted before: read the spec for what's actually new (the capability-description layer), and bring your existing distributed-systems discipline for everything else. The protocol will not protect you from a slow, unauthenticated, or badly versioned remote agent any more than gRPC protected you from a slow, unauthenticated, or badly versioned microservice. It just gives the whole industry a shared name for the contract.
