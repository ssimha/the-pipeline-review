THE PIPELINE REVIEW ARCHITECTURE

Beyond JDBC: why agents need both a driver (MCP) and a dictionary (OSI)

ODBC and JDBC solved how applications connect to databases. Agents have the same problem twice over — how to connect, and what the numbers actually mean once they arrive.

SIRISH SIMHA — ssimha.github.io
MCPthe driver
OSIthe dictionary

Every data engineer of a certain age remembers the moment ODBC and JDBC stopped being "nice to have." Before them, every application had its own bespoke driver for every database — a combinatorial mess. ODBC/JDBC didn't move the intelligence anywhere; they just gave everyone a common wire format to talk to a database, regardless of vendor.

Agentic AI is going through the exact same growing pain right now, except the mess isn't just "how do I connect" — it's also "how does the agent know what the numbers it gets back actually mean." Two standards are converging to solve this, and people keep conflating them. Let's separate them cleanly, with a retail example simple enough that the architecture stops being abstract.

01 Two very different jobs

The driver
MCP
Model Context Protocol — the connectivity layer. A standard way for an agent to call a tool or read a data source, regardless of what's behind it. The ODBC/JDBC equivalent.
The dictionary
OSI
Open Semantic Interchange — the meaning layer. A shared, vendor-neutral definition of what a metric like "net revenue" actually is, independent of which engine computes it.
Worth being precise about

MCP never uses an LLM. An MCP server is deterministic code — it receives a structured request, executes a lookup or a query, and returns a structured result. The only place an LLM shows up is in the agent sitting on top of MCP, deciding which tool to call and interpreting what comes back. MCP is the action layer; the agent is the reasoning layer — same way a JDBC driver has no opinion about the business logic that decided to run a query.

02 A retail example

Say a store manager asks an agent: "What was our net revenue for the North region last month, and how does that compare to active customers?"

Without semantic grounding, the agent has to guess from raw columns — amount, discount, refund_flag — and infer what "net revenue" means. Different runs, different answers. Hallucination with a straight face. Here's the flow once OSI is resolved by the MCP layer instead:

Request flow — store manager query, resolved
AGENT (LLM)
"I need net_revenue and active_customer count — region: North, period: last month"
↓MCP tool call · JSON-RPC · no LLM involved
MCP SERVER (deterministic)
Looks up "net_revenue" against the OSI definition: gross_sales − discounts − refunds
↓generates the query for whichever engine sits behind it
WAREHOUSE / DB
Executes → structured result → back to agent

The agent never touches a raw table. It asks for a named, governed metric and gets back a number it can trust — with enough structure to explain how that number was derived if the manager asks "why."

03 Two ways to wire OSI in

This is where it gets practical, and where most teams will actually live.

OSI-native tools

The tool reads OSI YAML definitions directly and resolves them internally — the MCP server in front is a thin passthrough. dbt Labs open-sourced MetricFlow as the OSI reference implementation; Cube, AtScale, and Looker are on the same path. If your stack already runs one of these, OSI compliance is close to "turn it on."

OSI-patched tools

Most real estates run an older warehouse or a plain schema with zero concept of semantics — and won't become OSI-native anytime soon. Here the intelligence lives in the MCP server itself: it reads the OSI YAML and translates it into whatever query the legacy backend already understands. The old system never knows OSI exists.

For most teams patching an existing warehouse into an agent stack, the patched pattern — OSI's intelligence sitting inside the MCP server, same role an ODBC driver played translating a common interface into a vendor-specific dialect — is where you'll actually start.

04 Why this cuts hallucination

The failure mode OSI targets isn't the agent being "dumb" — it's the agent being forced to infer business logic from raw schema every single time, with no way to stay consistent across runs. Ground it in a shared definition instead, and there's nothing left to guess.

05 A semantic layer for agents — not the one your BI team already has

This is the distinction that trips people up, because "semantic layer" already means something in the BI world. Your existing semantic layer — inside Tableau, Power BI, Looker dashboards — is built for humans: optimized for click-through exploration and visual consistency, usually inside one vendor's walled garden.

OSI sits underneath that, as the canonical, tool-agnostic source of truth both the human-facing layer and every agent's MCP tools draw from:

Top — built for humans
Common / BI semantic layer
Tableau, Power BI, Looker dashboards — click-through exploration, visual consistency
↑ both draw from the same underlying definitions ↑
Bottom — built for machines
OSI
Vendor-neutral YAML: net_revenue, active_customer, churn_rate — defined once, consumed by agents, MCP servers, and query engines

Define "net revenue" once at the bottom. The dashboard and the agent both inherit it. Nobody re-derives it twice, and nobody drifts.
