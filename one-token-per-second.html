One Token Per Second: I Ran a 744B Model on My Laptop and It Was Painfully, Beautifully Slow

A dev named JustVugg built Colibri, a tiny C program that runs Z.ai's GLM-5.2 — a 744-billion-parameter model — on a laptop with no GPU. Here's what it actually is, when it's genuinely useful, and when it's just a party trick.

TL;DR

Colibri runs GLM-5.2 (744B params, MIT-licensed, made by Z.ai) on ~25GB of RAM and zero GPU, by streaming most of the model off your SSD instead of loading it all into memory. It's real, it's clever, and it's slow — think one token every few seconds. Great for batch jobs and air-gapped work. Useless for anything you'd want to chat with.

Okay so here's a fun one for your Tuesday coffee. Somebody actually built a way to run a 744-billion-parameter model — the kind that normally needs a rack of GPUs — on a regular laptop. No CUDA, no cloud, no credit card. Just a single C file and a lot of patience.

Wait, who made what?

Two different things, so let's untangle them:

  • GLM-5.2 is the model. It's built by Z.ai (formerly Zhipu AI, a Chinese lab), released in June 2026 under an MIT license — meaning anyone can download the weights and run them, no strings attached. It's genuinely good, especially at coding — it beats or matches GPT-5.5 on several long-horizon coding benchmarks, and it's the strongest open-weight model on the leaderboards right now.
  • Colibri is the engine — a separate open-source project by a developer going by JustVugg. It's not a general-purpose runtime like llama.cpp; it's purpose-built, hardcoded even, to run GLM-5.2 specifically. Single C file, about 2,400 lines, zero dependencies.

Put them together and you get a 744B model answering questions on a machine that has no business running it.

How does it not just... run out of memory?

GLM-5.2 is a Mixture-of-Experts model — only about 40 billion of its 744 billion parameters are actually "awake" for any given token. Most engines still load the whole thing into GPU memory anyway because that's fast and simple. Colibri does the opposite: it keeps the small core of the model in RAM (about 10GB) and streams the rest — the specific experts each token needs — straight off your SSD, on demand. Like Netflix doesn't download the whole movie before playing frame one.

It's not fast. Nobody's claiming it's fast. The trick is that "slow and possible" beats "fast and impossible" for a surprising number of jobs.

Okay but is it actually useful, or just a cool demo

Both, honestly — depends what you're doing with it.

Where it earns its keep

  • Overnight batch work. Summarizing a document pile, classifying a backlog, drafting reports nobody's watching in real time. If it runs while you sleep, who cares if it's slow.
  • Air-gapped or locked-down environments. Places where calling any external API is a hard no. Slow-and-local beats fast-and-not-allowed.
  • The one gnarly query that's worth the wait. A contract review, a security audit, something you'd otherwise pay a consultant for. A few minutes of machine time is still cheap.
  • Kicking the tires before you spend real money. Want to know if GLM-5.2 can even do your task before you commit to GPU rental or an API contract? Test it slow and free first.

Where it falls flat on its face

  • Chat, agents, anything interactive. A coding agent making rapid tool calls needs speed. This gives you the opposite of speed.
  • Your SSD will hate you. Streaming hundreds of gigabytes off disk repeatedly is not what a consumer NVMe drive signed up for. Fine occasionally, bad continuously.
  • It's a black box you can't fully audit. MIT license means no legal restrictions, but you're still running a giant weights file from a Chinese lab — you can inspect the engine code, not really the model's "judgment."

Bottom line: Colibri isn't trying to replace your production stack, and it shouldn't. It's a proof of concept that huge MoE models don't strictly need a GPU cluster to exist — they just need somewhere to wait. If your task can wait too, that's a genuinely useful trade. If it can't, this is a fun Saturday project and nothing more. Know which one you're doing before you start the run.
